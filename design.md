# Design Guidelines

- Keep common task reporting policy in the editable global Agent Guide at data/devkits/AGENTS.md, visible in Settings → Rules; launchers must not append a separate hidden copy. Seed it only when creating a missing Guide and preserve user edits or intentional emptiness. Newly started local Tasks sessions receive only their run-scoped tasks-cli.cjs reporting command and --skill manual in their task prompt. The CLI reuses the live Tasks owner bridge rather than editing shared.json. Agents report doing, waiting, done or fail with a concise message; waiting maps to Doing plus Action Required. Native idle/done or a turn ending never completes a reported task. Preserve explicit final outcomes, reject stale/deleted/archived/stopped run reports, and make final retries idempotent. Keep bounded execution and activity histories and show interrupted sessions without inventing success. Existing conversations use the same stored progress and can adopt reporting on their next user request. Handoff and automatic account fallback are outside this version.

- Explicit conversation resume preserves the archive until Tasks observes the newly opened native tab and a reporting agent alive after a two-second startup grace period, then restores its exact profile/task link. Keep failed or timed-out launches retryable and suppress duplicate pending resumes; restoring a card alone never launches a program.

- Tasks owns an optional date-only Due date, validated as local YYYY-MM-DD and editable in task details (blank clears it). Calendar projects nonarchived task due dates as read-only all-day markers linked to Tasks, never duplicate stored events. Done markers show their status, archived markers hide, Restore uses the same date, and deletion removes the marker. Clicking a due marker opens Tasks; edit its date there.

- Schedule time in a task detail or card menu opens the existing Calendar event composer with an explicit stable task link and a suggested title. Calendar owns each independent time block; one task may have multiple events. Editing, moving, unlinking or deleting an event never changes task progress, due date or execution. No event starts an agent automatically. Preserve normal @task references separately from explicit scheduled-task links. Linked events display current task names/status, including Archived or Deleted task/Unavailable task, while retaining saved event titles, times and readable fallback labels. Task archive/delete never removes independent Calendar events. Calendar reads the public Tasks projection, including sanitized deletion markers, and never mutates Tasks records.

- When an opened folder is outside Git, discover Git repositories in its immediate child folders, including linked worktrees. Keep the project, file tree and conversations at the opened folder. Show a full-width 32px-high Select for repositories, with its label left-aligned and chevron at the right edge, above the Git panel's Changes/History tabs, even for a single child repository. The field fills its row within an 8px horizontal inset, matching native Popup window-edge clearance so a right-edge dock never shifts only the list. Its list matches the measured trigger width and opens directly below it without an additional horizontal offset or vertical gap. Select one repository at a time, remembering its relative folder per machine/project and falling back to the first available name. Changes, History, Graph, branch, credentials and remote operations use that selected repository; never combine repositories' changes. Changing repositories clears the previous repository's Git tabs and opens the selected repository's working diff, preserving file tabs. Ignore outdated discovery and Git results. Existing projects already inside Git retain their current behavior; nested parent/child repository selection is outside this change.

- SYSTEM and USAGE clients send subscription and refresh commands only while their service view is mounted in the current layout. Closing a client stops renewal and lets its existing five-second lease expire, without sending cleanup commands that could be dispatched after the provider is removed. Uninitialized clients send nothing. Returning to a layout with the service resumes subscriptions for open clients.

- The Add session Auto row shows Auto · followed by the account it would currently choose, with that account's provider icon. Refresh this preview when the menu renders and resolve the choice again on activation using the latest quota and settings.

- Share local Codex MCP settings through Herdr's `data/devkits/codex-mcp.json`. Settings → Agents offers Shared MCP… only on the base Codex row. Use a native dialog with one JSON editor for common servers. All accounts and named agents use the same servers; there are no account or agent exceptions. Use enabled=false on a complete shared server object to disable it for everyone. Ignore legacy profiles entries when loading and remove them when saving. Save with revision checking; cancel discards edits. Before starting a local Codex session, including Tasks, read the shared file and use a finite settings helper to synchronize common servers into that account’s config.toml. Keep complete transports even when disabled so background naming can read them without launch arguments or a running MCP service. Include the built-in herdr_tasks transport in that same synchronization; keep it managed by Devkits rather than requiring a Shared MCP entry. Track synchronized values in the same revision-checked config write; remove deleted shared entries only while their values remain managed, preserving unrelated account MCPs and independently edited entries. Explicit launcher arguments retain priority. Migrate selected existing local servers once with backups, selecting one shared transport and retaining unrelated settings in place.

- MantisBT loads issues in pages of 20. Show loading feedback for the active view and retain existing rows during pagination. Show an empty state only after a successful load; when loaded pages contain no open issues but another page exists, keep Load more available with an explanation. Fetch at most one page per View Issues load. View Issues' Filters offer Fetch all issues, which reads every remaining page with progress and Stop, because the MantisBT REST API ignores handler, status and sort parameters; Filters follow MantisBT's filter table: Reporter, Assigned To, Status, Category, Priority and Severity, each a label cell above a multi-select dropdown listing the loaded issues' values with [any] and [none], plus Reset Filter and a result count. They appear only once all pages are loaded, apply immediately and filter locally. A finished read is saved to data/devkits/mantisbt-issues.json per server and project (discarded when the token changes, five most recent kept) and shown at once on the next open; Refresh rereads it while keeping the current list until it finishes. Column headers sort the loaded list locally. Cache compact project lists in memory and persist them with their connection settings; never retain full project API responses. For five minutes, use the saved list without a request. After expiry, show saved projects immediately while updating in the background with an Updating projects indicator. Keep cached projects searchable if the refresh fails. Apply the latest search to refresh results, ignore late responses after closing, and discard persisted lists when credentials or the server change.

- MantisBT opens View Issues by default, showing the selected project's open issues for all assignees, including when the previous session used My View. My View remains available for issues assigned to the current user. Connection settings save the server URL and API token locally without requiring a successful API request. Keep saved credentials after connection failures, prefill them when reopening settings, and label the action Save.

- Open a local Calendar dialog from the calendar icon in the bottom status bar, before Tasks and independently of the selected project. Reuse Tasks' Linear palette, sans-serif font, rounded controls and compact geometry as a scoped exception to Sera. Provide remembered Day, Week and Month views, Today and previous/next navigation by the active period, and a fixed-width right-side agenda/editor for the selected day. Day and Week show a scrollable 24-hour axis, a separate all-day row and side-by-side overlapping events, clipping multiday events at each midnight. The month grid starts Monday. Selecting any month cell, including a neighbouring month's date, changes only selection and never rebuilds a different month; only Today, period navigation, an explicit view switch or saving an event reveals a different period. Clicking the backdrop closes only the topmost Calendar or event creation Dialog and discards its unsaved edits. All creation actions open a separate 560px Dialog with title, start/end dates and times, an All day checkbox and optional notes; existing event chips open their editor in the right sidebar. Drag a blank Day/Week timeline to preview and create a range snapped to 15 minutes, including reverse and cross-day selections. Drag across month cells or the all-day row to create an inclusive all-day date range; a single month click still only selects its date. Account for zoom and scrolling using each painted column's bounds, cancel a selection on Escape or leaving its grid, and never save until Create is chosen. Initialize new events with an empty required title, including events created from dragged ranges. Preserve existing event names and explicitly supplied draft titles. Show a visible required-title hint directly below every blank title field and disable Create/Save for blank or whitespace-only titles. Keyboard or programmatic submission still validates the title, focuses the field and preserves the dialog and range preview. Typing a title clears that error and enables Create/Save. Save commits edits, Cancel discards, and Delete removes that local event. Keep the parent calendar, its released range preview and any pending inline edits mounted while a creation Dialog is open. A released range stays highlighted behind the Dialog, including during form validation errors; clear only that Dialog's preview after successful creation or dismissal by Cancel, Escape, the close button or backdrop. Track pending ranges in their owning calendar view, never as saved events, and isolate cleanup between calendar windows. Dismissing the modal closes only that layer. Date ranges include the end date for all-day events; timed events use the computer's local time zone. Retain committed events in Herdr's local shared storage across reloads and restarts, rechecking event revisions before editing or deleting to preserve other windows' changes. Escape cancels an open editor before closing Calendar. Typing @ in the title or notes opens a native task picker directly below that @ glyph, with a focused search field, task names and project labels. Anchor to the native inline glyph layout so shaped text, previous task labels, newlines, wrapping, input scrolling and zoom determine the position; never anchor to the entire field or estimate character widths. Remove the temporary positioning token on dismissal or save, preserving the plain text, other task tokens and the return caret. Search active Tasks across local projects, including imported and agent-thread tasks; hide archived tasks from new selections. Focus the search after the picker appears. Each Up/Down press moves the highlight by exactly one result, Enter inserts the selected native inline token without submitting the event, and Escape dismisses only the picker while preserving the draft. Restore ordinary input keyboard behavior when the picker closes. Clicking outside dismisses the picker. Persist the task identity and UTF-16 token ranges with the event so editing surrounding text or deleting a token keeps links consistent. Scope identity to machine, project folder and task ID rather than its name. Existing saved tokens display the current task name and open its project’s Tasks detail, including Archived when applicable; creation drafts stay open when tokens are clicked. Retain readable labels for unavailable tasks and show an inline error on attempted navigation. Do not request Google sign-in, call external services, schedule agents or start tasks.

- Remember the selected Asana/MantisBT issue per Devkits project folder, source project and normalized server. Reopening the browser or reloading its mod restores that issue by fetching fresh details after the connection and binding load. Closing the browser retains selection; explicitly returning to the issue list or dismissing details clears it. Never persist credentials or task content as selection state.

- Each source browser owns a Field display section in its Settings / My Account page. Remember visible fields and their order separately for List columns, Asana Board cards and Task details, keyed by source project ID and normalized MantisBT server. Keep task titles visible. Offer native checkboxes and grip handles for drag ordering, highlight the drop target and save only on release; support Alt+Up/Down on the focused handle and cancel on Escape or leaving the field list; changes save immediately and do not save or discard connection edits. Read project custom-field definitions on entering settings, include fields found on loaded tasks, show loading/retry feedback, and ignore obsolete responses after switching projects or closing. Standard fields retain their defaults; custom fields start visible in details and hidden in lists/cards. Retain preferences for temporarily unavailable fields. Preserve field IDs, names, types, raw values and display values through source reads, import drafts and confirmed local task snapshots, regardless of visibility; never infer local Tasks priority or progress from source custom fields. Render field preferences in each source UI: Asana uses its own underlined tabs and compact property rows; MantisBT uses a separate blue-header widget with category table headings, alternating rows and its own buttons. Share field state and operations only, never a common settings layout. Resolve MantisBT custom-field types from project definitions, format date values for reading and retain their raw values in snapshots. MantisBT details retain the standard metadata header grid and property rows, then Summary and Description; custom fields follow as full-width name/value rows in their configured order, never packed into the standard three-column grid. Activities rows stretch both author and comment cells to the full row height, with comment text aligned to the top and a 12px gap between consecutive activity records.

- Use Asana → MantisBT → Calendar → Tasks order in the bottom status bar, with Tasks at the right of this group. Open Asana and MantisBT directly from labeled buttons with their brand icons when a project is selected. Each opens its own source browser bound to that project without opening Tasks first. Clicking the backdrop closes only the topmost source browser or popup, discarding unsaved connection edits without importing a task. Keep source entry buttons out of the Tasks header; importing still opens an editable Tasks draft.

- SYSTEM, Asana, MantisBT, Tasks, Calendar and Usage are independent Herdr mods, each with its own native entry point and implementation. SYSTEM owns sampling/settings/details and publishes session snapshots through a bundled consumer SDK; each host owns its mount location, visibility and renderer choice. Source mods own their connections and browsers, return serializable task snapshots through a caller-owned channel, and let the consuming Tasks UI decide how to save or launch work. Import opens an editable draft and creates a local Todo only after confirmation. Tasks owns records, task/thread relationships, status inference, policies and execution preparation in a service that remains active while the board is closed. The shell renders Sidebar groups from Tasks’ published project-scoped snapshots and owns placement, layout changes and native navigation. Calendar owns events and reads the same public task index for mentions, waiting for Tasks to validate a reference before closing its dialog. Keep state/policy code out of both the shell and Calendar; communicate through serialized requests and navigation events.

- Keep system monitoring settings in the monitor’s own Settings page, opened from Interface settings or the SYSTEM context menu; omit a standalone System action from the bottom status bar; omit System from Agent settings. Devkits owns a SYSTEM visibility master switch and its Sidebar/Status bar locations in Interface settings, with quick choices in its right-click menu, reachable only on SYSTEM sidebar region and status metrics. Never attach SYSTEM’s menu to the whole sidebar or status bar, unrelated controls or empty workspace areas. Interface settings remains reachable in the sidebar footer when both monitor mounts are hidden. Each SYSTEM right-click menu contains only its own region’s controls: the sidebar menu toggles sidebar visibility and chooses Overall CPU/Per logical CPU mode; sidebar widgets always use Compact presentation with no style picker; bottom metrics show only status-bar visibility and the monitor-settings link. Keep these placement and presentation controls out of SYSTEM Settings. Allow both mounts at once, sharing sampling and history. Save Devkits display choices separately from monitoring preferences, migrating the old placement, style, CPU mode and preferred sidebar height once without resetting widget choices. The status bar contains one compact line of selected widgets in their saved order: CPU/GPU/RAM percentages and short disk/network rates, with no model names, capacities, subtitles or history charts. Click a metric for its details; keep Monitor settings reachable through Interface settings even when every widget is hidden. Keep the other status controls reachable in narrow windows. Sidebar monitoring offers 2 rows, 4 rows, 6 rows and Auto height (default), retaining six rows for a later switch to presets. Do not expose pixel inputs or a custom-height mode. Presets use the native measured heights of the first N available cards in saved order, including header and insets, sharing measured Compact card heights across CPU modes because their row geometry is identical. Leave no blank rows when fewer cards exist. Bound the viewport to the available height while reserving the project list, Usage and footer without changing the saved preset. Auto height follows the actual laid-out card heights, capped by available space. Read sizes from plain layout wrappers whose native identity includes the presentation and CPU mode, so a mode change receives fresh size callbacks. Reuse equal-height Compact measurements during the switch and update the outer viewport when measurements arrive; native scroll content does not supply an intrinsic outer height. Do not add a bottom spacer below the final card. Row presets measure plain per-card layout wrappers rather than native Button controls. It must not expand into unused space; overflow scrolls only when the content exceeds that cap. The 6px top-border drag area snaps to the nearest row preset on release, accounting for zoom; double-click restores four rows. Scroll only when content overflows. Preserve the row count and mode through visibility, style and location changes. Preserve widget choices, interval and histories when toggling either mount. Normalize previously saved Inline/History sidebar styles to Compact without changing other preferences. Keep inline metrics in the bottom status bar; the sidebar always uses Compact widgets and retains its row count, sizing mode and resize handle.

- In Sidebar mode, keep a configurable SYSTEM monitor for this computer below account USAGE and above the sidebar footer. Its chart button and the Monitor settings link in Interface settings stay accessible when every widget is hidden. Monitor Settings retains durable metric visibility/order, 1/3/5/10-second sampling, CPU detail graph mode and logical-processor selection; the consuming mod owns mount visibility, widget style and widget CPU mode. Use CPU, RAM, GPU, Storage, Network, Disk activity, Battery and Sensors as the default order, migrating the former default while preserving custom orders. CPU, RAM, GPU and Storage start visible; Network, Disk activity, Battery and Sensors start hidden. Default to three-second sampling, P/E CPU details and all logical processors. Devkits defaults to Sidebar only, Compact widgets, Per core CPU and Auto height, retaining six rows for presets. Provide one Reset button on the SYSTEM page of Interface settings that immediately restores both these display defaults and the provider-owned monitoring defaults through a serialized command, without clearing readings or history. Battery appears only when detected and selected. Use themed history lines and concise values. In the sidebar, RAM and Disk show total capacity at the right of their title; RAM usage and percentage and disk read/write speeds sit below, including in Compact mode. Use RAM consistently for the system memory module in navigation, cards and Settings. Reorder widgets with the same grip handles and highlighted drop targets as the existing Agents/Models settings; commit on drop, support Alt+Up/Down on the focused handle, and cancel on Escape or leaving the list without changing visibility. Disk capacity is the system volume capacity; show that volume’s physical disk model on the sidebar model line and in Disk/Storage details, never the first mounted disk image or unrelated drive. Cache static disk inventory between samples. Read/write rates cover physical disks. GPU shows the busiest adapter’s memory capacity at right and its name/utilization below, with that adapter's used GPU memory at the lower left (explicitly unavailable when unreported); distinguish the Apple unified pool and Windows shared limit from dedicated VRAM, never sum adapter capacities. Show OS-reported RAM DDR/LPDDR type beside RAM, and show CPU, RAM, GPU and Storage model lines in Compact sidebar widgets. RAM includes the reported manufacturer, module part number and speed; show the same part number in RAM details. Keep GPU adapter name/utilization visible on separate lines so the chart never crowds the model name. Compact widgets show RAM, GPU and Storage with consistent 20-segment horizontal usage bars and numeric percentages, alongside CPU bars. Label the sidebar CPU modes Overall CPU and Per logical CPU: Overall CPU uses one 20-segment usage bar for the average across all logical processors, while Per logical CPU uses a separate vertical usage bar for each selected logical processor. Both CPU modes use the same title/model/usage three-row layout as RAM, GPU and Storage. Put the graphic and overall percentage together in the right-aligned 116px usage area, with 12px-high bars in both modes; never add a full-width CPU-only graph row or duplicate the percentage in the title. Explain the distinction in Interface settings; display selection never changes CPU capacity. RAM and Storage bars use capacity utilization; GPU uses the busiest adapter utilization, independently of its reported memory capacity. Keep each resource model and capacity visible, with used capacity for RAM/Storage. Fill bars from current values, including partial segments; unavailable readings leave them empty with unavailable percentages. Keep resource histories in details. Cache static memory metadata instead of running hardware inventory every sample; unavailable types/capacities stay explicit. The monitor uses 90% of the window width, with a three-column Overview (two in narrower windows), equal-height cards, resource pages with charts and metadata side by side, and two-column Settings. Keep navigation top-aligned, processor name before core counts, and the title/footer fixed around scrolling content. Close with Done, Escape or the backdrop. CPU details offer Total, Logical processors and P/E groups: use Task Manager-style individual history charts with identical tile widths/heights, including incomplete final rows; single-choice view controls must work with both mouse and keyboard, show physical cores, logical processors and sockets separately, and label P/E only from OS-reported topology. Keep SMT siblings distinct and respect Windows processor groups. A homogeneous/unknown topology stays unclassified. Selected processors affect presentation only, never affinity or available CPU capacity. Preserve choices across reloads/hardware changes. Share bounded three-minute history and warm readings in session memory, persisting only preferences. Coalesce reads, use elapsed counter deltas, split missing/long-gap history, reject reset/hotplug spikes, count one active network interface and exclude disk images from macOS physical I/O. Do not add tooltips.

- Storage details lists physical disks in compact cards (two columns when wide, one when narrow) by stable OS device identity, with model, type, connection and physical capacity, then their mounted partitions/volumes with used and available space. Default the sidebar to the system volume, and centralize per-volume Show in main panel checkboxes, combined/individual physical disk I/O choices and CPU/GPU/SSD temperature switches directly in the right column of the monitor Settings page, below its monitoring controls. Keep Overview focused on metric cards; never require navigating from Settings to another page to access these choices. Keep these choices reachable when all widgets are hidden or readings are unavailable; detail pages retain readings and metadata without duplicate display controls. Remember multiple choices and render a separate card for each selected volume. Settings offers all-disk combined output or individually selected physical disks and CPU/GPU/SSD temperature visibility alongside its widget, sampling and CPU controls. Controls take effect immediately and re-enable their module when selected. Persist stable reported identities as fingerprints rather than model names, mount letters or raw serials; keep unavailable selections explicit and recover them when the device returns. Never substitute another device at the same mount letter or mix histories across targets. Maintain the existing row-height measurement and module ordering for every expanded card. Never treat C: and D: as separate disks when they share one device, attach an unknown volume to the first disk, or add shared APFS pool capacity repeatedly. Show shared or unmapped volumes separately, and show unmounted disks without invented usage. Use the bundled systeminformation inventory and read-only OS metadata; APFS physical-store identities may use a finite diskutil/plutil supplement. Cache static inventory for five minutes, refreshing storage mapping when the mounted-volume set changes; preserve other hardware caches. Do not scan user files, run benchmarks, write test data, start services or persist live storage history.

- Keep every SYSTEM sidebar widget in the same compact title, device/source and readings three-row geometry, including Network, Disk activity, Battery and Sensors. Keep secondary capacity panels and stacked metadata at most 560px wide and sensor tables at most 880px wide, aligned to the start rather than stretching sparse rows across the dialog. Network and Disk activity include two-series 116px by 12px sparklines beside compact direction-labeled rates in the readings row; color each rate label and value to match its curve (download/read in the resource color, upload/write in the secondary purple); use real throughput history and a shared rate scale, without inventing a utilization percentage. Show GPU memory used separately from GPU utilization; place disk and network rates below their device names, and battery charge beside its state. Sensors shows individually labeled CPU, GPU and SSD temperatures with explicit missing readings instead of an anonymous GPU temperature. Preserve saved visibility and hide absent batteries. Refine the existing monitor details in the restrained style of [macOS Activity Monitor](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac): clear chart units, subtle grids, consistent time axes, matching series legends, aligned device metadata and used/available capacity bars. Keep CPU/GPU utilization distinct from memory capacity. Retain the existing navigation, palette, topology views and three-minute local history; charts preserve gaps, show unavailable states, and retain real sample timing. Explain missing Windows CPU temperatures in Sensors: the current reader needs an already-running LibreHardwareMonitor WMI provider; available NVIDIA readings are GPU-only.

- Use the pinned, bundled systeminformation package as the common reader for CPU metadata, RAM usage/layout, filesystem capacity, drive models, network counters, battery and fallback GPU metadata. Keep native supplements only for missing logical CPU P/E identities, GPU engine/64-bit memory identities, physical disk I/O that excludes images, detailed RAM breakdown/pressure, battery temperature and opt-in sensors. Refresh static inventory at most every five minutes; preserve elapsed counter deltas across finite reader processes. All hardware monitoring remains read-only: no process scheduling/affinity, resource limits, power settings, fan control, driver installation or service startup. macOS CPU P/E mapping uses actual IODeviceTree logical IDs and cluster types, with sysctl core/socket counts. The Windows native supplement uses local read-only CPU/disk/GPU performance counters, DXGI adapter memory descriptions and GetSystemCpuSetInformation; raw CPU timers retain 64-bit precision and identify each processor by group plus logical index. Missing providers leave only their readings unavailable, preserving supported metrics. Optional Sensors adds CPU/GPU/SSD temperatures, fans and power with explicit source/unit labels and no guessed replacements. CPU/GPU summaries use the highest returned sensor, not battery temperature; sensor points are thermal zones, not CPU cores. On macOS, build/cache the bundled read-only SMC helper using existing Apple Command Line Tools, without starting an installer or requesting elevation; unsupported keys/chips stay unavailable. Preserve the Stats MIT attribution for ABI/key references. Windows uses available NVIDIA query endpoints and an already-running LibreHardwareMonitor WMI provider when present, without installing or launching either. NVIDIA fan percentage is not RPM. Sensor polling is opt-in because it adds work. Never claim Windows live validation based solely on macOS or fixture tests.
